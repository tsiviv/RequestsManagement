# ביצועים

בדיקת היעילות של שתי פעולות ה-API המרכזיות על 100,000 רשומות, האינדקסים שנוספו ולמה, ה-Bottlenecks שנמצאו והשיפורים המוצעים עם המדידה שלהם.

## סביבה ושיטה

- **נתונים:** 100,000 פניות מה-Seeder הדטרמיניסטי (`dotnet run -- --reseed`). כ-200 ארגונים, 15 מטפלים, התפלגות סטטוסים לא אחידה (55% Completed).
- **שרת:** SQL Server LocalDB 15.0 (2019), collation `SQL_Latin1_General_CP1_CI_AS`, על מחשב פיתוח. המספרים המוחלטים תלויים במכונה. ההשוואה בין הגרסאות היא מה שחשוב.
- **השאילתות:** בצורה ש-EF Core מייצר, עם פרמטרים דרך `sp_executesql`, כפי שהאפליקציה שולחת אותן.
- **"לפני / אחרי" אינדקסים:** כל שאילתה רצה פעמיים: כמו שהיא, ועם `WITH (INDEX(0))`, שכופה סריקה מלאה של הטבלה (Clustered Index Scan). כך רואים מה הייתה עולה אותה שאילתה בלי האינדקסים, בלי לשנות סכמה.
- **ריצה חמה:** כל גרסה רצה פעם אחת לחימום, והריצה השנייה היא שנמדדת, כדי שקריאות דיסק לא יעוותו את ההשוואה.
- **מדדים:**
  - `SET STATISTICS IO`: logical reads, כלומר עמודים של 8KB שנקראו. זה המדד היציב ביותר.
  - `SET STATISTICS TIME`: CPU ו-elapsed.
  - `SET STATISTICS PROFILE`: האופרטורים ב-Plan בפועל.
- **שחזור:** [perf/measure-queries.sql](perf/measure-queries.sql) מודד את השאילתות, ו-[perf/measure-improvements.sql](perf/measure-improvements.sql) את השיפורים המוצעים.

## תוצאות

### פעולה 1: `GET /api/requests` (רשימה)

כל בקשת רשימה מריצה שתי שאילתות: עמוד (`OFFSET/FETCH`) ו-`COUNT` לאותו `WHERE`.

| תרחיש | עם אינדקסים | Plan | בלי אינדקסים | Plan |
|---|---|---|---|---|
| ברירת מחדל, עמוד 1 (החדשים קודם) | **71** reads, 2 ms | Index Scan מסודר + 20 Key Lookups, בלי Sort | 2,539 reads, 394 ms | Clustered Scan + **Sort** |
| מטפל + סטטוס New + יולי | **386** reads, 2 ms | Index Seek | 2,539 reads, 46 ms | Clustered Scan + Sort |
| ↳ `COUNT` | **17** reads, 4 ms | Seek על שני אינדקסים + Hash Match | 2,539 reads, 45 ms | Clustered Scan |
| סינון לפי ארגון | **71** reads, 2 ms | Index Seek | 2,539 reads, 61 ms | Clustered Scan + Sort |
| מיון לפי ארגון, עמוד 1 | **71** reads, 2 ms | Index Scan מסודר, בלי Sort | 2,539 reads, 1,400 ms | Clustered Scan + Sort |
| חיפוש טקסט חופשי, עמוד | 606 reads, 5 ms | Index Scan לפי תאריך עד שנמצאו 20 התאמות | 2,539 reads, 1,093 ms | Clustered Scan + Sort |
| ↳ `COUNT` לחיפוש | 2,539 reads, **528–1,106 ms** | Clustered Scan, אין אינדקס שעוזר | 2,539 reads, 1,060 ms | Clustered Scan |
| `COUNT` ללא סינון | 536 reads, **60–71 ms** | Index Scan של האינדקס הצר ביותר | 2,539 reads, 61 ms | Clustered Scan |
| עמוד עמוק 2,501 (OFFSET 50,000) | **153,454** reads, 335 ms | Index Scan + **50,020 Key Lookups** | 2,539 reads, 395 ms | Clustered Scan + Sort |

### פעולה 2: `GET /api/requests/summary` (Aggregations, כשהערך לא ב-Cache)

| שאילתה | עם אינדקסים | בלי אינדקסים |
|---|---|---|
| `COUNT(*)` | 536 reads, 60 ms (Index Scan) | 2,539 reads, 66 ms |
| `GROUP BY Status` | 625 reads, 86 ms (Index Scan + Stream Aggregate, בלי Hash) | 2,539 reads, 101 ms (Hash Match) |
| `GROUP BY Priority` | 621 reads, 80 ms (Index Scan + Stream Aggregate) | 2,539 reads, 92 ms (Hash Match) |

סה"כ כ-230 ms לחישוב. לכן ה-Summary נשמר ב-Cache, וקריאה מה-Cache עולה 19–26 ms מקצה לקצה (ראו README, סעיף Cache).

**מה רואים:**
- **תרחישי הסינון והמיון הנפוצים** יורדים מסריקה של כל הטבלה, 2,539 עמודים ועד 1.4 שניות, ל-17 עד 386 עמודים ו-2 עד 5 ms.
- **ב-Plan שלהם אין Sort:** האינדקס כבר בסדר המבוקש.
- **ה-Aggregations** סורקים אינדקס צר במקום את הטבלה, ובגלל הסדר שלו מקבלים Stream Aggregate במקום Hash Match.

## האינדקסים שנוספו ולמה

| אינדקס | נוסף בשביל |
|---|---|
| `IX_Requests_Status_CreatedAt` | סינון לפי סטטוס עם "החדשים קודם", ו-`GROUP BY Status` ב-Summary |
| `IX_Requests_Priority_CreatedAt` | סינון לפי עדיפות עם "החדשים קודם", ו-`GROUP BY Priority` |
| `IX_Requests_AssignedTo_CreatedAt` | סינון לפי מטפל (ומטפל + טווח תאריכים), ורשימת המטפלים ב-`filter-options` |
| `IX_Requests_OrganizationName_CreatedAt` | סינון ומיון לפי ארגון, ורשימת הארגונים ב-`filter-options` |
| `IX_Requests_CreatedAt` | רשימת ברירת המחדל (החדשים קודם) וטווח תאריכים בלבד |
| `IX_Requests_UpdatedAt` | מיון לפי עדכון אחרון |
| `IX_RequestStatusHistory_RequestId_ChangedAt` | היסטוריית שינויים של פנייה: Seek וקריאה בסדר הפוך, בלי Sort |

**עקרונות שהנחו את הבחירה:**
- **העמודה המובילה היא זו שמסננים לפיה בשוויון, והשנייה היא סדר המיון.** כך אותו אינדקס משמש גם ל-Seek, גם לטווח וגם לסדר.
- **כל מפתח non-clustered מסתיים במפתח ה-clustered (`Id`).** לכן ה-tiebreaker `Id` בכל מיון לא דורש Sort.
- **אין אינדקס לכל עמודה:** מיון מותר רק לפי עמודות שיש להן אינדקס תומך (הרשימה ב-README, סעיף "מיון").
- **מחיר בכתיבה:** כל שינוי סטטוס מעדכן את `IX_Requests_Status_CreatedAt` ואת `IX_Requests_UpdatedAt`. זה מקובל, כי שינויים נדירים בהרבה מקריאות.

## Bottlenecks והצעות לשיפור

### 1. `COUNT` של חיפוש טקסט חופשי: עד שנייה לכל חיפוש

**הבעיה:**
- `search` מתורגם ל-`Title LIKE '%x%' OR OrganizationName LIKE '%x%'`. עם `%` בהתחלה התנאי אינו sargable, ולכן אף אינדקס לא עוזר.
- את העמוד עצמו מוצאים מהר (5 ms): הוא נסרק לפי תאריך ועוצר אחרי 20 התאמות.
- ה-`COUNT` חייב לעבור על כל 100,000 השורות, ועולה 528–1,106 ms. השונות בין ריצות גדולה. כל חיפוש, אחרי ה-debounce, מחכה לזה.
- רוב הזמן הוא CPU של השוואת מחרוזות לפי ה-collation, לא קריאת עמודים: אותם 2,539 עמודים נקראים בכל המקרים.

**שיפור נמדד, collation בינארי בתנאי:**

```sql
WHERE Title COLLATE Latin1_General_100_BIN2 LIKE @search
   OR OrganizationName COLLATE Latin1_General_100_BIN2 LIKE @search
```

| | זמן | תוצאה |
|---|---|---|
| collation רגיל | 528 ms | 10,968 |
| BIN2 | **117 ms**, פי 4.5 מהר יותר | 10,968, זהה |

**המחיר:** החיפוש הופך לרגיש לאותיות גדולות/קטנות ולניקוד/סימנים.
- **בעברית אין משמעות לאותיות גדולות/קטנות**, ולכן אין שינוי בתוצאות על הנתונים הנוכחיים.
- **בטקסט באנגלית** "Invoice" ו-"invoice" כבר לא יתאימו זה לזה. אפשר לפתור זאת עם עמודה מחושבת מנורמלת (`UPPER`), שעליה מחפשים.

**לטווח ארוך, Full-Text Search** (`CONTAINS` עם אינדקס Full-Text):
- **יתרון:** חיפוש לפי מילים ותחיליות שמשתמש באינדקס, בלי סריקה.
- **מחיר:**
  - הסמנטיקה שונה: התאמה לפי מילים, לא לפי כל תת-מחרוזת.
  - דורש רכיב Full-Text בשרת.
  - האינדקס מתעדכן באופן אסינכרוני.
- **מתי כדאי:** כשהטבלה גדלה בסדר גודל.

**חלופה משלימה:** ספירה מקורבת או חסומה לחיפוש, למשל "יותר מ-1,000 תוצאות", במקום ספירה מדויקת.

### 2. עמוד עמוק: OFFSET 50,000 קורא 153,454 עמודים

**הבעיה:**
- `OFFSET` לא יכול לדלג: SQL Server קורא ומשליך את כל השורות שלפני העמוד.
- עם האינדקס על `CreatedAt` כל שורה כזו עולה Key Lookup לטבלה, כי העמודות שבתוצאה לא נמצאות באינדקס.
- כך עמוד 2,501 עולה 50,020 Lookups, ובסה"כ **פי 60 יותר קריאות מסריקה מלאה** (153,454 לעומת 2,539).
- זה ה-Bottleneck שמתעצם ככל שהטבלה גדלה.

**שיפור נמדד, Deferred Join:** קודם בוחרים את 20 המזהים של העמוד מתוך האינדקס הצר בלבד, בלי Lookups, ורק אז שולפים את 20 השורות המלאות:

```sql
SELECT r.* FROM Requests r
WHERE r.Id IN (SELECT Id FROM Requests ORDER BY CreatedAt DESC, Id DESC
               OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY)
ORDER BY r.CreatedAt DESC, r.Id DESC
```

| | קריאות | זמן |
|---|---|---|
| היום | 153,454 | 335 ms |
| Deferred Join | **319** | **13 ms** |

**אותן 20 שורות בדיוק** (נבדק בסקריפט).

**מימוש ב-EF Core:** `pageIds = sorted.Select(r => r.Id).Skip(skip).Take(take)`, ואחריו `db.Requests.Where(r => pageIds.Contains(r.Id))` עם אותו מיון. EF מתרגם את זה לאותה תת-שאילתה, בלי שינוי ב-API.

**חלופה: Keyset Pagination**, שבה מעבירים "אחרי `(CreatedAt, Id)` האחרונים" במקום מספר עמוד:
- **יתרון:** עלות קבועה בכל עומק.
- **מחיר:** אי אפשר לקפוץ לעמוד שרירותי. ה-API וה-UI (paginator עם מספרי עמודים) היו משתנים.

### 3. `COUNT` בכל בקשת רשימה

**הבעיה:**
- ברשימת ברירת המחדל העמוד עולה 2 ms, אבל ה-`COUNT` של כל הטבלה עולה 60–71 ms (536 עמודים).
- בבקשה הנפוצה ביותר הספירה היא רוב העלות.

**הצעה:** כשאין אף פילטר, ה-`COUNT` זהה ל-`total` שב-Summary, שכבר שמור ב-Cache ומתבטל בכל שינוי. אפשר להשתמש בו ולחסוך את השאילתה. עם פילטרים הספירה כבר זולה (17 עמודים בדוגמה), כי היא נעשית ב-Seek.

### 4. שילוב סטטוס + מטפל

- **הבעיה:** `Status` אינו חלק מ-`IX_Requests_AssignedTo_CreatedAt`, ולכן הוא נבדק רק אחרי Key Lookup לכל שורה של אותו מטפל וטווח (386 קריאות בדוגמה, במקום כמה עשרות).
- **שיפור אפשרי:** `INCLUDE (Status)` באינדקס הזה.
- **המחיר:** עוד אינדקס שמתעדכן בכל שינוי סטטוס.
- **מתי כדאי:** בזמנים הנוכחיים (2 ms) זה לא מוצדק. יהיה כדאי אם הסינון המשולב הזה יהפוך למרכזי.

## מגבלות המדידה

- **LocalDB על מחשב פיתוח, משתמש אחד:** הזמנים המוחלטים לא מייצגים שרת ייצור. ההשוואות היחסיות, ובעיקר מספרי הקריאות, הן מה שחשוב.
- **השונות בזמנים גבוהה** בשאילתות שה-CPU שלהן כבד, למשל `COUNT` החיפוש: 528 ms בריצה אחת ו-1,106 ms באחרת. לכן גם הקריאות מדווחות, והן יציבות.
- **לא נבדק עומס מקבילי.** במקביליות גבוהה סריקות מלאות פוגעות גם בשאילתות אחרות, כך שהפער בין "עם" ל"בלי" אינדקסים רק גדל.
